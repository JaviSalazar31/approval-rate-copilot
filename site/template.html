An AI analyst for a payments team. Ask why card approvals dropped and it answers with the cause, the cost and the next step, using SQL anyone can check.

The problem

The feeds disagree

A payment orchestrator earns money only when payments are approved. When approval drops, the payments team needs three answers fast: how much it is costing, why it is happening and what to change.

Getting there means joining the orchestrator log with three acquirer feeds that disagree on almost everything: time zones, amount formats, column names and the codes for the same issuer answer. The pipeline turns all of that into one canonical status per attempt, with a versioned map that remembers which rule classified each decline.

One row of that map, highlighted in the table, is the latent cause of the incident below.

Two causes stacked

Acquirer B approves Colombian debit less often than A, and a decline-code map released a week earlier had quietly stopped B's “do not honor” declines from being retried on a second acquirer. The copilot does not split the drop between the two, so here is my estimate. Had B's {{incident.b05_window_failures|int}} “do not honor” declines been retried and recovered at B's Colombian recovery rate in the 28 days before the bug ({{incident.b05_co_recovery_rate|pct0}}), about {{incident.b05_lost_in_window|int}} more payments would have been approved: about {{incident.drop_from_missing_retries_pp|abs1}} points ({{incident.missing_retries_low_pp|abs1}}–{{incident.missing_retries_high_pp|abs1}} with other reasonable rates). The warning came six days early

Retries of B's “do not honor” declines fell from 100% to {{incident.b05_first_day_cascade_rate|pct0}} on 6 August, the day the new map went live, and to 0% from the next day. Daily approval barely moved, so a dashboard that watches only outcomes stayed green. A cascade alert that watches the retry mechanism itself flagged it in the next morning's run and in every daily run until the fix, but in the scenario nobody owned it, so nobody acted. Over those nine days about {{incident.b05_lost_recoveries|round10}} approvals (≈ USD {{incident.b05_lost_recoveries_usd|k0}} of approved volume) that a retry would normally have recovered were lost in Mexico and Colombia, most of them before the visible incident.

The copilot

One question, five checks

The copilot is a Databricks Genie agent on the gold tables. I designed the diagnostic method as five Unity Catalog SQL functions. The model decides what to check, runs the functions and, when it needs to, its own SQL, and explains the result; every query is shown under the answer.

  1. 1 · sizeHow big is the drop?fn_drop_impactLost approvals and USD against a baseline period.
  2. 2 · driversWho moved?fn_approval_driversAcquirer, issuer, brand, 3DS, segment and routing version, split into rate and mix effects.
  3. 3 · declinesWhich codes grew?fn_decline_shiftFirst-attempt failures by acquirer and reason, before and during.
  4. 4 · retriesDid retries still work?fn_cascade_healthRetry and recovery rates, and how the map classified each code.
  5. 5 · changesWhat changed nearby?fn_changes_nearRouting, risk, mapping, releases and partner notices around the window.

Evaluation

Tested before trusted

{{eval.total}} questions in four groups, each with a scoring rule: 16 with ground-truth SQL, 4 guardrails with an expected behavior. A Claude model (Sonnet) played the copilot with exactly the instructions, tables and functions the Genie agent gets; a harness ran its SQL on the pipeline output, and a separate model (Claude Opus) graded every answer, including whether each number came from a query. Each run could read only its instructions and its own query results. Then the same questions ran on the deployed Genie agent (the G columns). Every answer, query and verdict is published in the repository.

Decisions

Product calls that shaped it

ADR-06

Answers come from SQL, not from documents

The questions are quantitative, so answers must be exact and auditable. The diagnostic method lives in tested SQL functions; the model chooses what to run, adds its own SQL when needed, and explains.

ADR-08

Alert on the safety net too

A broken retry barely moves daily approval. An alert on the retry rate itself flagged the map bug in its first daily run, six days before the visible incident. The retry policy must also respect the card networks' reattempt rules.

ADR-01

A versioned decline-code map

Every attempt keeps the map version that classified it. That is what lets the copilot say “05 was soft under v2.2 and hard under v2.3”.

ADR-07

Anomalies that respect volume

A day is flagged only if the drop is large in points, unusual for its history and unlikely for its volume. On the 90 days used to tune it: one flag, the planted incident. A three-hour issuer outage needs hourly detection.

ADR-12

Teach the agent with structure, not only words

On Genie, short text rules held less well than they had offline. Each fix went into the most structured place that could carry it: a function's output or parameters, an example query, a description. The benchmark went from {{eval.genie_first}} to {{eval.genie_passed}} of {{eval.total}}.

ADR-09

Evaluate before rollout

A fixed question set with ground truth runs before every change to instructions, functions or tables. Instructions that read better can still answer worse.

Next

What I would build next

  1. Grow the held-out set and run it on every change: more questions per group and several samples each, and fixes for the chat-mode gaps it found: a table with no text, and a text “NULL” passed for an optional parameter.
  2. Pilot on real data with three analysts for four weeks, after short interviews, measuring time to diagnosis against today's process.
  3. Hourly detection on the busiest segments, so a 14:00 drop surfaces within hours instead of the next morning.
  1. A routing guardrail that ramps changes 10% → 50% → 100% and compares approved volume, not fee bps, at each step.
  2. Owners for alerts. In the scenario the retry alert fired nine days in a row and nobody acted: every alert needs a named owner and a runbook entry.
